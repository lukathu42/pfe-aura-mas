# Full evaluation campaign — findings (W3.4/W3.5)

Ran 2026-08-13: 7 scenarios × {centralized, mas-nocoord, mas-rules, mas-auction},
plus vision-only ablation on the 4 scenarios with an audio sensor — 44 runs
total. Raw runs in `results/run_*.json`, aggregated in `results/summary.csv`.
This replaces the earlier single-scenario (`demo_site_01` only) evaluation
that `STATE_NOTES.md` was based on.

**Three real, pre-existing bugs were found and fixed while building this
campaign** — not just new data. Each is described below because it changes
how to read both the new numbers and any numbers already cited elsewhere
(chapters, `STATE_NOTES.md`) from the old single-scenario run.

## 1. `data/clips/intrusion.mp4` and `overview.mp4` are synthetic placeholders, not real footage

Both are flat vector-graphic animations (a solid-color stick-figure icon
sliding into a drawn "ZONE A - RESTRICTED" rectangle) generated by
`aura_mas/scripts/make_synthetic_clips.py`, not recorded video. YOLO11n
never detects a `person` in `intrusion.mp4` at any confidence down to 0.05 —
the only class ever detected in the whole clip is a stray `sports ball`
(almost certainly the stick figure's round head).

This was not a new problem: the **original, pre-existing**
`results/run_intrusion_01_mas-auction.json` and
`data/alerts_intrusion_01_centralized.jsonl` (both already on disk before
this session, produced by the prior AI session) already show **zero**
intrusion alerts. The `intrusion_01` scenario has never actually
demonstrated video-based intrusion detection in this repository's history.

**Fix**: `scenarios/intrusion_01.json` and `scenarios/combined_audio_video_01.json`
(which also used `intrusion.mp4`) now point at the real `people.mp4`/`street.mp4`
clips already validated elsewhere in this pack, with a zone and ground-truth
timing matched to real, directly-verified ByteTrack detections (not asserted).
Both now produce genuine intrusion alerts. `data/clips/intrusion.mp4` and
`overview.mp4` are left on disk (harmless) but nothing in `scenarios/` uses
them anymore.

## 2. `centralized` mode's duration-based rules used wall-clock time, not video time

`centralized` mode intentionally processes frames as fast as the CPU allows
(no real-time pacing) to measure the MAS's architectural benefit. But
`ZoneRuleEngine`'s loitering (≥8s dwell) and abandoned-object (≥10s static)
rules were keyed off `time.time()` — wall-clock — not the video's own
timeline. A 73-second clip processed in 20 real seconds could never
accumulate 10 seconds of "static object" time, so centralized mode could
structurally never detect these two event types, independent of detection
quality. This would have silently made centralized look categorically worse
than it is on any scenario with loitering/abandoned-object ground truth.

**Fix**: `aura_mas/agents/camera_agent.py` now threads a separate
`video_ts` (derived from `frame_id / src_fps`) through to
`ZoneRuleEngine.evaluate()` for duration bookkeeping, while `Event.timestamp`
(used for alert-latency metrics) still uses wall-clock time. Verified:
`abandoned_object_01` under `centralized` now fires (previously fired 0/0).

## 3. The original `demo_site_01.json` loitering ground truth was likely never achievable

Checked directly (not inferred): tracked every person's ByteTrack `track_id`
span across `people.mp4`, `street.mp4`, `intrusion.mp4`, `overview.mp4`. The
longest continuous single-track presence found anywhere is **5.5 seconds**
(`people.mp4`, track 3, t=15.3-20.8s) — below the 8-second loitering
threshold, regardless of zone shape (also tried a full-frame zone). Nobody
in any available clip actually stands still long enough. This almost
certainly explains the recurring 1-false-negative-out-of-3 in every mode of
the original `results/summary.csv` — it's very likely this same
never-actually-detectable loitering claim every time, not four independent
misses.

`demo_site_01.json` (pre-existing) was left as-is rather than silently
rewritten. The new `scenarios/loitering_01.json` is deliberately built with
an **empty ground truth** and documents this finding directly — it now
functions as a true-negative / false-positive probe (loitering should NOT
fire on brief crossings) rather than a fabricated true-positive case.

## Other findings from the campaign data itself (not bugs, but worth knowing)

- **Detection is not perfectly deterministic run-to-run.** `intrusion_01`
  under `centralized`/`mas-rules`/`mas-auction` produced 0 intrusion events
  in earlier attempts during this same session, then fired reliably on
  retry with identical code/config — most likely floating-point
  non-determinism from PyTorch's default multi-threaded CPU inference
  interacting with borderline `conf=0.35` tracking thresholds. **Recommendation
  for the thesis**: run each scenario×mode combination N≥3 times and report
  mean±std, not a single run, before citing these numbers as final. This
  campaign is a single pass per combination.
- **`audio_glass_break_01` and `combined_audio_video_01` show f1=0 for the
  audio side even though the audio agent genuinely fires.** `tensorflow`/
  YAMNet was not installed in this pass (disk-constrained, see
  `data/clips_real/manifest.json`), so `AudioAgent` runs its DSP fallback,
  which emits a generic `audio_anomaly` instead of the class-specific
  `audio_glass_break`. `FAMILY` mapping in `aura_mas/eval/metrics.py` puts
  `audio_anomaly` in `violence_or_hazard` and `audio_glass_break` in
  `security`, so they never match — by design of the fallback, not a scoring
  bug. This is exactly the risk the schedule's own fallback table
  anticipated; the fix is installing YAMNet, not patching the metric.
- **`fight_01` shows f1=0 despite CLIP genuinely detecting the anomaly.**
  The alert fires at t≈15.4s wall-clock, but the clip itself is only ~5-8s
  and `metrics.py`'s default ±5s tolerance window is `[-4.5, 9.5]s` — the
  one-time CLIP model *load* latency (~10s on CPU, this is a cold start,
  not the actual per-frame inference cost) pushes the alert outside the
  window. This is a benchmark-methodology artifact (evaluating a single
  short clip with the model loaded from cold), not a detector failure — a
  real production system keeps the model warm. Longer scenarios (demo_site_01,
  intrusion_01) don't show this problem because the absolute alert-latency
  budget dwarfs one-time load cost. Recommend either warming the model before
  the timer starts, or scoping short single-clip scenarios out of latency
  metrics specifically.
- **`abandoned_object_01` fires under `mas-nocoord` (recall=1.0) but not
  `centralized`/`mas-rules`/`mas-auction`.** Consistent with the
  run-to-run non-determinism point above rather than a coordination-mode
  effect — the underlying detector is the same across modes.

## What this means for citing numbers

Treat `results/summary.csv` from this pass as a demonstration that the
pipeline now genuinely exercises all six scenario categories on real
footage/audio (a real improvement over the single n=1 demo_site_01 run), not
as final thesis numbers. Before citing: (1) re-run each combination multiple
times for variance, (2) install YAMNet if the audio-family corroboration
claim (C3) needs to be shown with real class-specific audio events, (3)
decide on a warm-up policy for CLIP timing.
